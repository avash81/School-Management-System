# Document 09 — Security Specification

## Trust chain

```text
identity → authenticated session → role/permission → school tenant
→ academic/resource/relationship scope → lifecycle policy → allow/deny + audit
```

## Mandatory controls

- Argon2id password hashing; secure random single-use hashed reset tokens; account/session revoke/expiry; generic login/recovery errors; rate limits and lock policy.
- Server-side authorization before loading/mutating resource; tenant filters inside queries; assignment scope for staff and relationship scope for portals.
- TLS in deployed environments; HttpOnly/Secure cookies where used; CSRF controls for credentialed cross-site operations; secure headers/CORS allowlist.
- DTO validation plus domain validation; parameterized ORM/database access; output encoding/CSP/XSS defenses; dependency/secret scans.
- Private object storage; server keys, MIME/magic-byte/size/checksum/malware validation; time-limited authorized downloads; no public default.
- Secrets manager, least-privilege service identities, encryption at rest/in transit, backup encryption, redacted logs.
- Append-only audit for sensitive actions; support/maintenance access requires approval/reason/time limit.

## Threat response

Tenant leak, privilege escalation, stale write, malicious upload, brute force, session abuse, provider outage, export/download disclosure, and OCR false match have tests, monitoring, alerting, remediation, and incident runbooks. Legal/privacy retention and offboarding require qualified review before production.

### HI-03 Operational Controls (resolved for the re-audit gate)

#### 1) CSRF strategy detailed spec

- Default browser posture: `SameSite=Lax` for session cookies for standard browser navigation and authenticated stateful requests.
- For cross-site form submissions or API-based clients that cannot rely on same-site semantics, require a double-submit token: one signed CSRF cookie and one request header value generated from the session secret.
- `SameSite=Strict` is allowed only for highly sensitive flows such as account security or maintenance endpoints, and only when the app can tolerate no cross-site navigation continuity in the browser.
- All state-changing endpoints must reject missing or mismatched tokens with `403 CSRF_TOKEN_MISSING` or `403 CSRF_TOKEN_INVALID` before any business mutation executes.
- Token rotation occurs on login, refresh, and privilege switch, and the previous token is invalidated immediately to reduce fixation windows.

#### 2) Encryption / key management SOP

- Database encryption: PostgreSQL is deployed with either pgcrypto-managed data encryption or provider-managed volume encryption at rest. Secret columns (password hashes, refresh hashes, token hashes, raw export links) are never stored in plaintext.
- MinIO/S3 object storage: object keys are random UUID-based, not user-controlled; bucket policy denies public read; signed URLs are short-lived and generated server-side with explicit expiry.
- Secret material is kept in a managed secrets store (Vault, AWS Secrets Manager, GCP Secret Manager, or equivalent), not in repository files or Docker layer defaults.
- Rotation schedule: root credentials rotate every 90 days; DB credentials rotate every 30 days for shared environments; service-to-service tokens rotate every 24 hours or on privilege changes.
- Key ownership: platform ops owns storage secrets; platform security owns signing secrets; app owners own configuration and tenant-specific defaults; rotation is recorded in the audit stream and release notes.

#### 3) Log redaction rules baseline

- Redaction list includes 22 known secret keys and 15 PII fields; this baseline must be extended before production signoff with jurisdiction-specific fields such as Aadhaar, PAN, UDISE, tax IDs, or national ID numbers as required by local law.
- Logger middleware masks all values for keys matching `password`, `secret`, `token`, `apiKey`, `authorization`, `cookie`, `session`, `refreshToken`, `email`, `phone`, `dob`, `aadhaar`, `pan`, `studentUid`, and other known PII keys.
- Raw request bodies are never logged for auth, reset, upload, or export flows. Only structured metadata is emitted alongside the request ID and correlation ID.
- Security logs are stored in append-only audit channels; no audit row may be modified or deleted by application code.

#### 4) Rate-limit budget tiers by role and endpoint

| Tier          | Scope                                                          | Default budget | Window     | Notes                                                         |
| ------------- | -------------------------------------------------------------- | -------------- | ---------- | ------------------------------------------------------------- |
| `auth-public` | login, password reset, MFA bootstrap, refresh challenge        | 20 requests    | 15 minutes | Hard throttle before any DB lookup or credential verification |
| `reads`       | list/search/detail read APIs                                   | 200 requests   | 60 seconds | Additional tenant and teacher-scope filters remain mandatory  |
| `mutations`   | create/update/delete academic, marks, result, document actions | 100 requests   | 60 seconds | Intended to cap bulk updates and noisy import bursts          |
| `admin-ops`   | support, maintenance, system settings, impersonation           | 50 requests    | 60 seconds | Requires additional system audit and approval context         |
| `export`      | report generation and signed-document retrieval                | 20 requests    | 60 seconds | Intended to prevent export abuse and PDF rendering storms     |

- The API layer enforces limits at the global `APP_GUARD` level via Redis-backed storage, and a memory fallback is permitted only for local warm-up environments.
- All 429 responses include a retry-after header and a generic error envelope; they never reveal whether an account exists or a resource is valid.

#### 5) Break-glass / Support access SOP

- Break-glass access is only granted via a dedicated `support_access_grants` record with required fields: `grantedByUserId`, `grantedToUserId`, `schoolId`, `reason`, `requestedAt`, `expiresAt`, `status`, `approvedBy`, `revokedAt`.
- The default lifetime is 2 hours and may only be extended by a platform owner or designated support approval authority. No support grant may remain active beyond the approved expiry window.
- The access request must follow a two-person approval rule: one support operator requests, one platform owner approves, and both actions are recorded in the audit trail.
- Every break-glass session is tied to a unique session context, and access is automatically revoked when `expiresAt <= now` or when support review closes the case.
- Support actions are logged with a separate audit tier, including the actor, tenant, reason, window, and final disposition. No silent support access is permitted.
- Any cross-tenant or out-of-scope data access attempt during break-glass generates an explicit security incident record and triggers escalation to the platform security owner.

#### 6) File malware / quarantine contract

- Files are accepted only after a strict validation pipeline: allow-list MIME type, 3-way verification of file extension + MIME + magic bytes, size limits, and page-count checks where relevant.
- The first storage destination is a quarantine bucket, not the production document store. Only files that pass the scan and review gate may move to approved storage.
- A malware engine such as ClamAV or managed equivalent is required before a file becomes usable for import or report generation. If the scan engine is unavailable, the file remains quarantined and is never promoted without manual review.
- On suspicion or positive detection, the file is marked with `status='rejected_infected'`, the original bytes are deleted or isolated, the uploader is notified, and the event is appended to the audit stream.
- Quarantine review tasks and the final approval decision are auditable and role-restricted; no end-user can promote a quarantined file without an approved workflow.
