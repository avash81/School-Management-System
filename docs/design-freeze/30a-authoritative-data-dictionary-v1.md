# CR-01A — Authoritative Data Dictionary v1.0

**Companion to:** `30-authoritative-database-specification-v1.md`.  
**Notation:** `uuid!` = required UUID, `text?` = nullable text, `ts!` = required `timestamptz`, `date?` = nullable `date`, `num(p,s)` = PostgreSQL `numeric(p,s)`, `jsonb?` = nullable JSONB. `SYS` means the standard columns defined in Document 30 apply. All school-owned FK references are tenant-composite as specified there. `SD` means soft-deletable; `APPEND` means no update/delete through normal application operations.

## Enum ownership

All listed status/type columns use PostgreSQL enums or check-constrained reference codes owned by migration. Their legal transitions are in Document 13 and CR-04. The initial enum families are: `school_status`, `user_status`, `student_status`, `teacher_status`, `enrollment_status`, `exam_status`, `mark_status`, `mark_attendance_status`, `result_status`, `upload_status`, `ocr_job_status`, `import_session_status`, `document_status`, `notice_status`, `notification_status`, `delivery_status`, `job_status`, `file_scan_status`, `review_task_status`, `approval_decision`, and `rounding_mode`. Enum additions are expand-only; removal requires replacement/check migration and data conversion.

## Required implementation verification queries

Before an FK/uniqueness migration is validated, migration owner must run and retain outputs for: tenant-parent mismatch count; orphan count by FK; duplicate active enrollment/roll/primary guardian/default configuration; missing snapshot for published result; duplicate idempotency key; unscanned file referenced by import; and legacy URL column references not yet linked to `file_objects`.
