# Document 03 — Complete Use Case Specification

## Catalogue and convention

The complete module catalog is [D0.4 Full Use Case Catalog](../architecture/d0-4-use-case-catalog.md), expanded by Parts 1–8. Every use case follows: ID, actor, goal, preconditions, trigger, main/alternative/exception flow, postconditions, permissions, rules, data, APIs/UI, and related use cases. This document fixes the shared convention and specifies the critical workflow use cases.

## UC-STU-001 — Admit and enroll student

**Actor:** school administrator or delegated staff. **Goal:** create a unique student and valid historical placement. **Preconditions:** authorized tenant; academic context exists. **Trigger:** admission submission.

Main: validate fields/identifiers → create student → validate guardian/placement → create active enrollment → audit. Alternative: create applicant without enrollment; link existing guardian. Exceptions: duplicate identifiers, invalid class/section/year, permission/tenant denial, concurrency conflict. Postcondition: student and requested enrollment both persist or neither does. Permission: `students.create` plus `enrollments.create`. Rules: BR-STU-001/002, BR-TEN-001. Data/API/UI: Student/Guardian/Enrollment; `POST /students`; admission screen. Related: transfer, promotion, archive, portal profile.

## UC-ASSIGN-001 — Assign teacher context

**Actor:** school administrator. **Goal:** establish teacher’s allowed academic scope. Preconditions: active teacher/year/class/section/subject. Main: validate all tenant/year relations → create assignment → audit → roster becomes available. Exceptions: inactive/conflicting assignment or invalid offering. Postcondition: assignment is active; no broad access is granted. Permission: `assignments.manage`. Rules: BR-ASSIGN-001. Data/API/UI: TeacherAssignment/Offering; `POST /assignments`; assignment screen.

## UC-EXM-001 — Create and configure examination

**Actor:** exam coordinator or authorized school admin. **Goal:** create an exam and governed marks context. Main: select academic year → configure schedule/eligible offerings → attach versioned blueprint/components → open entry when valid → audit. Alternatives: draft/save configuration; delegate subject setup. Exceptions: invalid dates/components, incompatible configuration in use. Postcondition: exam is draft/scheduled/entry-ready, not published. Permission: `exams.manage`. Data/API/UI: Exam/ExamSubject/Schedule/Blueprint; `/exams`; exam workspace.

## UC-MRK-001 — Save and submit manual marks

**Actor:** assigned teacher. **Goal:** record a revisioned draft or submit complete marks. Preconditions: entry open, active assignment, eligible enrollment/component. Main: load scoped roster → validate value/status → save revision/audit → submit validates completeness and transitions state. Alternatives: absent/exempt/not-submitted. Exceptions: range/status error, stale revision, closed exam, unrelated roster. Postcondition: draft or submitted mark provenance exists. Permission: `marks.write`, `marks.submit`. Rules: BR-MRK-001–004. Data/API/UI: MarkEntry/Revision; `/marks`; marks grid. Related: review, correction, result calculation.

## UC-IMP-001 — Create and process marks import

**Actor:** teacher/exam coordinator. **Goal:** create a provisional, reviewable import. Main: authorize selected context → validate/scan/store source → create idempotent session/job → preprocess/extract/map → match → confidence/business/duplicate validation → route to review/ready. Alternatives: upload CSV/XLSX mapping or OCR image/PDF. Exceptions: malicious/unsupported source, provider/worker failure, no/ambiguous match. Postcondition: no official marks change. Permission: `imports.create`. Data/API/UI: Upload/ImportSession/Record/Match/Job; `/imports`; upload/review queue.

## UC-IMP-002 — Approve and import reviewed marks

**Actor:** authorized approver. **Goal:** atomically apply accepted provisional rows through the marks engine. Main: confirm review state/scope → revalidate current references/lifecycle → idempotent transaction creates/revises permitted marks → session complete → audit/outbox. Alternatives: reject/cancel/retry; correction workflow for locked records. Exceptions: any invalid row/reference/conflict causes no partial official application unless policy defines itemized approved batches. Postcondition: durable import outcome and provenance. Permission: `imports.approve`, appropriate marks authority. Rules: BR-IMP-001/002. Related: marks review/correction.

## UC-RES-001 — Calculate, approve, and publish result

**Actor:** exam coordinator calculates; configured approver publishes. **Goal:** produce reproducible official result. Main: load eligible approved marks/rule version → calculate components/total/grade/GPA/pass → persist calculated revision → review/approve → validate target set → publish immutable snapshot/audit/outbox. Alternative: queue large calculation; reopen with reason. Exceptions: incomplete marks, invalid policy, missing approval, stale state. Postcondition: calculated or published version; publication may trigger documents/notifications. Permission: `results.calculate/approve/publish`. Data/API/UI: Result/Snapshot/GradeRule; `/results`; results workspace.

## UC-DOC-001 — Generate and verify document

**Actor:** authorized staff requests; recipient downloads; verifier checks minimal status. **Goal:** create historically traceable private output. Main: authorize source/published eligibility → choose approved template → record source/template versions → queue renderer → checksum/private store → history/audit → authorized download. Alternative: batch generation/retry/revoke/regenerate. Exceptions: missing template/source, render/storage failure, expired/revoked verification. Permission: `documents.generate/download`; verifier requires opaque token only. Data/API/UI: TemplateVersion/GeneratedDocument/History; `/documents`, `/verify`; document center.

## UC-NOT-001 — Publish notice and notification

**Actor:** authorized publisher. **Goal:** publish approved audience-specific communication. Main: draft → validate audience/content/dates → optional approval → publish/audit → create notification intents → queued delivery status. Exceptions: restricted audience, provider failure, expired schedule. Postcondition: notice remains auditable; delivery is independently tracked. Permission: `notices.publish`. Data/API/UI: Notice/Intent/Delivery; `/notices`; notice composer.

## UC-OPS-001 — Controlled support/maintenance

**Actor:** platform operator. **Goal:** safely administer platform without routine academic bypass. Main: request reason/approval → time-bounded support or maintenance scope → perform allowed operation → audit → expire/revoke. Exceptions: unresolved incident escalates; maintenance blocks normal mutation by policy. Permission: `platform.support/maintenance`. Data/API/UI: SupportAccess/MaintenanceState/AuditLog; `/platform`; operations console.

## UC-AUTH-001 — Create authenticated session (login)

**Actor:** any user (unauthenticated). **Goal:** establish a valid, scoped session cookie with correct device metadata. **Preconditions:** server env is healthy; `loadEnvironment` passed Zod parse; Redis session store is reachable for throttler; user record exists and is not `suspended`/`locked`; credential not expired. **Trigger:** user submits login form with email + password (or SSO future).

Main: throttle tier `auth-public` (20/15min) applied before any DB read → generic email lookup returns one user row (tenant-agnostic, then scoped by school) → Argon2 verify (9 parameters, constant time) on first match only → credential invalid: branch to Exception A → credential valid but user status `inactive`/`suspended`/`locked`: branch to Exception B → create `sessions` row (id=uuid, userId, schoolId, expiresAt=now+24h, device=summarizeDevice(ua), ip=x-forwarded-for||req.ip, lastActiveAt=now, hashed refresh token) → create audit_log row `action=session.create` with userId+schoolId → set session cookie `HttpOnly Secure SameSite=Lax path=/` cookie name=`${COOKIE_PREFIX}session` value=session.id → also set CSRF double-submit cookie (non-HttpOnly) for state-changing mutations → return `{data: {user, roles, permissions, scopes}, meta: {requestId}}`. Alternatives: remember-me checkbox extends session expiresAt to 7 days; SSO OIDC future (Document 29 §87 strategy extension); user has multiple school accesses → first active school + offer switcher UI. Exception A (bad credentials): count +1 towards lockout in memory/RateLimiter → after 10 consecutive wrong: user.status=`locked` until reset by admin → always return same 401 error code `AUTH_INVALID_CREDENTIALS` (no account enumeration) → audit_log `action=session.fail`. Exception B (disabled user): return 401 `AUTH_ACCOUNT_DISABLED` generic text (no distinction suspended vs locked in message body) → audit_log `action=session.denied reason=suspended|locked`. Postcondition: exactly one `sessions` row created; session id has high entropy; cookie flags comply with CTL-02 D4 §3; audit event persisted. Permission: public endpoint (no permission; global ThrottlerGuard only). Rules: BR-AT-001, BR-AT-002, BR-AT-005, BR-TEN-001. Data/API/UI: `users`, `sessions`, `audit_logs`; `POST /api/v1/auth/login` Zod body `loginSchema` (email+password, unknown fields stripped); Login screen. Related: UC-AUTH-002 (refresh), UC-AUTH-009 (unauth denied), HI-03 THR-04 (brute force).

## UC-AUTH-002 — Rotate session via refresh token

**Actor:** authenticated user (browser background). **Goal:** transparently extend session lifetime without re-login; detect token replay. **Preconditions:** valid session cookie exists; hashed refresh token stored on session row matches supplied value; session.expiresAt within grace window (not more than 1h expired). **Trigger:** 401 `SESSION_NEEDS_REFRESH` intercepted by frontend interceptor or before expiry timer.

Main: find session by id from cookie → compare stored hashed refresh_token vs body-supplied token (timing-safe compare) → mismatch: Exception A (replay). → session.expired > grace: Exception B. → rotate: new refresh_token generated (random 48 bytes → sha256 hash); session row updated in-place: refreshTokenHash=new, lastActiveAt=now, expiresAt += 24h → audit_log `action=session.refresh`. → return new refresh_token + same sessionId (cookie untouched, HttpOnly remains). Alternative: frontend stores refresh_token in memory (not localStorage). Exception A (replay): invalidate session immediately (destroy row); emit audit_log `action=session.replay detected` severity=critical → return 401 SESSION_REVOKED → force logout UI. Exception B (beyond grace): destroy session row → return 401 SESSION_EXPIRED → redirect to login. Postcondition: session refresh_tokenHash rotates; replay impossible without server-side invalidate. Permission: valid session id (no extra RBAC). Rules: BR-AT-003. Data/API/UI: `sessions`, `audit_logs`; POST `/api/v1/auth/refresh` body `{refreshToken}`; Session recovery UI interceptor.

## UC-AUTH-003 — Password reset (single-use time-limited)

**Actor:** user with valid email. **Goal:** securely reset forgotten password via out-of-band email link. **Preconditions:** SMTP provider configured; user.email verified; no reset token used within last 60s (rate limit). **Trigger:** user clicks "Forgot password" → enters email → submits.

Main (step 1: request): throttle tier auth-public → always return 202 `RESET_REQUESTED` (no email-exists disclosure) → if email exists in users: generate token random 32 bytes hex → sha256 hash → create row password_reset_tokens(userId, tokenHash=sha256(token), expiresAt=now+15min, usedAt=null, singleUse=true) → send email with link `/reset?token={raw}&email={hinted}` → audit_log `action=password.reset_requested`. Main (step 2: confirm): user clicks link → UI loads reset form → POST `/api/v1/auth/password-resets/confirm` body `{token, newPassword}` → server lookup password_reset_tokens where tokenHash = sha256(token) AND usedAt IS NULL AND expiresAt > now → not found: Exception A → newPassword passes strength policy (Zod: min 12, 1 upper, 1 digit, 1 symbol) → hash with Argon2 → update users.passwordHash in same transaction → set password_reset_tokens.usedAt = now → invalidate all user sessions (delete sessions rows) → audit_log `action=password.reset_completed` + `action=session.invalidate_all reason=password_reset`. Alternative: admin-initiated reset for suspended users by SCHOOL_ADMIN only. Exception A: return 400 RESET_TOKEN_INVALID generic (no distinction expired vs used vs bad hash). Postcondition: password rotated; all prior sessions killed; token can never be reused; audit trail complete. Permission: public (step 1), valid bearer token (step 2, token itself). Rules: BR-AT-004. Data/API/UI: password_reset_tokens, users, sessions, audit_logs; POST `/password-resets`; `/password-resets/confirm`; Reset password screen.

## UC-AUTH-009 — Unauthenticated request denied

**Actor:** anonymous client, any endpoint path. **Goal:** consistent rejection across all protected surfaces without info disclosure. **Preconditions:** ThrottlerGuard runs before AuthenticationGuard order via APP_GUARD array. **Trigger:** request arrives at any protected controller or route not in public whitelist.

Main: AuthenticationGuard checks `req.cookies[sessionCookieName]` exists → missing → set WWW-Authenticate: Cookie realm="SchoolOS" → return 401 UNAUTHORIZED with standardized envelope `{error:{code:'AUTHENTICATION_REQUIRED', message:'Authentication required'}, meta:{requestId}}` → audit_log only if suspicious pattern (not on every miss to prevent log spam). Exception: cookie present but session row not in DB or expired → same 401 envelope code SESSION_EXPIRED vs cookie missing → code AUTHENTICATION_REQUIRED (slight distinction to support UX but never leak whether account exists). Alternative: refresh endpoint grace → AuthenticationGuard returns 401 SESSION_NEEDS_REFRESH (special code) instead of generic when session is within refresh grace. Postcondition: no data returned; response is always envelope JSON. Permission: N/A (before permission guard). Rules: BR-AT-005. Data/API/UI: all protected endpoints. Sign-in redirect handled by `@schoolos/ui` `<AuthBoundary>` HOC on 401 interception. Related: UC-AUTH-010.

## UC-AUTH-010 — Permission plus data-scope enforcement

**Actor:** authenticated user making an API call. **Goal:** authorization = (feature permission code) AND (applicable data scope) — never OR. **Preconditions:** AuthenticationGuard has already populated `req.user` with `{id, schoolId, roles[], permissions: Set<code>, scopes: {teacherClassIds?, teacherSectionIds?, teacherSubjectIds?}}`. **Trigger:** PermissionGuard `canActivate` method invoked per endpoint.

Main: PermissionGuard reads `@RequirePermissions(...codes)` metadata → `req.user.permissions` is a Set → every required code must be present (AND semantics) → any missing code: return 403 FORBIDDEN `PERMISSION_DENIED` → next: scope filter runs for teacher-scoped endpoints (marks entry, attendance, student search): e.g. POST `/marks` check markEntry's sectionId is in `req.user.scopes.teacherSectionIds` → not in scope: 403 OUT_OF_SCOPE → for GET endpoints: auto-append scope filters to prisma `where` clause via Prisma helper `withScope(where, user.scopes)`. Alternatives: school admin has scope=null (no restriction, can see all). Super admin cross-school: requires `platform.support` grant (UC-OPS-001). Exception: attempting cross-school id in path param → return 404 NOT_FOUND (not 403; prevents existence probe). Postcondition: every DB query binds authenticated schoolId; teacher-scoped queries additionally bind class/section/subject id arrays. Permission: explicit codes from Document 19 catalog. Rules: BR-AT-006, BR-AT-007. Data/API/UI: user_roles, role_permissions, user_scopes, teacher_assignments used to materialize req.user.scopes; all protected endpoints. Access denied screen with return-dashboard link. Related: UC-AUTH-011.

## UC-AUTH-011 — Tenant isolation (cross-tenant denial)

**Actor:** authenticated user of school A attempting to access school B data by any channel. **Goal:** zero cross-tenant leakage across 8 channels (Master Plan §2024–2046). **Preconditions:** every table has school_id; all services call prisma helper `tenant(schoolId)` (or explicit where schoolId) before any query; row-level security triggers enabled (Stage 2 migration future). **Trigger:** 8 possible channels: UI breadcrumb manipulation, API path param id, search query params, report filters, document URL signed token, file downloads, background job queue message tenant mismatch, notification target user wrong school.

Main (per query): Service-layer `schoolId = req.user!.schoolId!` (asserted non-null by guard) is bound to every find/count/update/delete → example attack: `GET /students/{schoolB_studentId}` → Prisma where: `{ id, schoolId }` → 0 rows → 404 NOT_FOUND returned (prevent existence enumeration). For background jobs: job payload carries schoolId; worker asserts `job.schoolId === user.schoolId` from worker-context user or throws JOB_TENANT_MISMATCH. For signed URLs: schoolId embedded in signed claims; verifier asserts match. For notifications: insert checks notification.recipientUserId → user.schoolId vs notification.schoolId. Alternatives: super-admin break-glass (UC-OPS-001) can switch schoolId context → audit_log `action=tenant_switch severity=high`. Exceptions: any row returned with mismatched schoolId → caught in `@Catch()` TenantLeakDetector interceptor (future unit test TC-SEC-001-C hardens) → logs CRITICAL + returns 500 TENANT_ASSERTION_FAILED + kills session. Postcondition: 0 rows ever leak to wrong tenant user. Rules: BR-AT-007. Data/API/UI: all tenant tables; all endpoints. Test family TC-SEC-001-A through TC-SEC-014 in HI-05 covers all 8 channels.

## UC-ACA-001 — Create non-overlapping academic year

**Actor:** school admin. **Goal:** one active year per school; dates non-overlapping with existing years. **Preconditions:** user has `academicYears.manage` permission; school exists. **Trigger:** POST `/api/v1/academic-years` with name + startDate + endDate + isActive.

Main: ZodValidationPipe parses `{name, startDate, endDate, isActive?:boolean}` → endDate > startDate (Zod refine) → DB check for overlapping existing years on same schoolId: `where schoolId AND startDate <= input.endDate AND endDate >= input.startDate count > 0` → overlap: Exception A → if isActive=true AND another row has isActive=true → Exception B → create row academic_year (school_id, name, start_date, end_date, is_active, row_version=1) → audit_log `action=academicYear.create`. Alternative: close prior active year automatically if user confirms (two-step endpoint: POST /activate → atomically unset old isActive + set new). Exception A overlap: 422 YEAR_DATE_OVERLAP with existing year id/name. Exception B double-active: 422 YEAR_ACTIVE_ALREADY_EXISTS with suggestion to deactivate. Postcondition: exactly 0 or 1 is_active=true row per school; dates disjoint. Permission: `academicYears.manage`. Rules: BR-AT-011. Data/API/UI: academic_years, audit_logs; POST `/academic-years`; Academic years screen.

## UC-STU-002 — Guardian link with single-primary rule

**Actor:** school admin. **Goal:** student may have N guardians but max 1 active primary. **Preconditions:** student exists; guardian email or phone uniqueness validated per school. **Trigger:** add guardian to an existing student.

Main: upsert guardian row (first_name, last_name, relation, phone, email) → if inserting new: schoolId + (email OR phone) uniqueness check → duplicate different student: Exception A → get current count of student_guardians rows where studentId, isPrimary=true → count ≥1 AND new row has isPrimary=true → Exception B → create row student_guardians (studentId, guardianId, isPrimary, isActive, emergencyContactOrder) → audit_log `action=student.guardian_link`. Alternative: swap primary atomically: UPDATE existing primary isPrimary=false + INSERT new isPrimary=true in same transaction on explicit `forcePrimarySwap=true` flag + confirmation. Exception A: 422 GUARDIAN_ASSIGNED_OTHER_STUDENT → with link to existing student id. Exception B: 422 GUARDIAN_PRIMARY_EXISTS → hint to use swap flag. Postcondition: at most one row (studentId, isPrimary=true); guardian contact details clean. Permission: `students.update`. Rules: BR-AT-017. Data/API/UI: guardians, student_guardians. POST `/students/{id}/guardians`. Student guardians screen. Related: UC-STU-001.

## UC-STU-003 — Enrollment uniqueness per academic year

**Actor:** school admin. **Goal:** a student has at most one active enrollment per academic year. **Preconditions:** student exists; class+section+academicYear offering exists for same school. **Trigger:** POST `/api/v1/enrollments` or during UC-STU-001 initial atomic admission.

Main: check existing enrollments rows where studentId, academicYearId, status IN ['active','enrolled','promoted'] → count ≥1 → Exception A → validate section.class.academicYearId === enrollment.academicYearId (cross-year mismatch) → Exception B → insert row enrollments (studentId, classId, sectionId, academicYearId, rollNo auto per section sequence, status='enrolled', enrolledAt=now) → audit_log. Alternative: transfer mid-year: archive old (status=transferred) + create new with transferReason + transferFromSchoolId (different school internal). Exception A: 422 ENROLLMENT_DUPLICATE_YEAR with existing enrollment id + status. Exception B: 422 ENROLLMENT_ACADEMIC_YEAR_MISMATCH → class belongs to Y but input is Y'. Postcondition: for any (student, year) tuple: 0 or 1 rows with status ∈ [active,enrolled,promoted]; historical remain readable. Permission: `enrollments.create`. Rules: BR-AT-019. Data/API/UI: enrollments; POST `/enrollments`. Enrollment history tab. Related: UC-STU-006 (archive).

## UC-MRK-005 — Mark approval workflow + no self-approve

**Actor:** reviewer (school admin / principal / exam coordinator — NOT the teacher who submitted marks). **Goal:** marks pass through approval steps; self-approve blocked by default policy. **Preconditions:** MarkEntry.status = `submitted`; approval_policies row linked to exam has defined steps[] with required roles per step. **Trigger:** POST `/api/v1/marks/{id}/approve` by authenticated reviewer.

Main: fetch approval_policy for exam → default policy.allow_self_approval = false → check policy.steps[i] against current step index → current user.id === markEntry.submittedBy → Exception A (self-approve) → user.roles does not contain step.requiredRole → Exception B → step through ordered steps until first incomplete: record approval_action (step=idx, userId, status=APPROVED, comment=optional) → if last step completed → markEntry.status = `approved`; publishedAt? not yet (UC-MRK-008 publish later) → else markEntry.status = `reviewed` → audit_log `action=mark.approve step=idx`. Alternatives: rejection: POST `/reject` body `{reason}` → markEntry back to `pending`; approval_action records REJECTED; policy with allow_self_approval = true (small-school config, explicitly set; audit_log severity=medium warning every self-approve). Exception A: 403 APPROVAL_SELF_FORBIDDEN. Exception B: 403 APPROVAL_ROLE_REQUIRED currentRole: X, need: Y. Postcondition: ordered approval_actions chain persisted; no mark reaches approved without last-step done. Permission: per-step role codes from policy (marks.approve). Rules: BR-AT-029, BR-MRK-001. Data/API/UI: approval_policies, approval_steps, approval_actions, mark_entries. POST marks/:id/approve; /reject. Marks review queue screen. Related: UC-MRK-001, UC-MRK-008.

### UC-TEA-001 — Teacher onboard with composite employeeId+school uniqueness + qualifications/documents atomic

**Actor:** school admin. **Goal:** create teacher with optional qualifications + uploaded documents in one transaction; employeeId uniqueness per school enforced. **Preconditions:** user has `teachers.create`; school exists. **Trigger:** POST `/api/v1/teachers` body with nested `qualifications[]`, `teacherDocuments[]` `fileObjectIds[]` references.

Main: Zod pipe validates teacher.employeeId (max 64 chars), firstName, lastName, dateOfBirth (past), dateOfJoining (not future), phone (E.164), email (email), status (active/inactive), subjectIds (scope later), classIds (homeroom scope later). → DB check `WHERE schoolId AND employeeId = input.employeeId AND deletedAt IS NULL count > 0` → duplicate row exists → Exception A. → Transaction: INSERT teachers (schoolId, employeeId, personal attrs, status) → for each qualification object: INSERT teacher_qualifications (schoolId, teacherId, degree, institution, major, yearOfPassing, gpa/division, fileObjectId?) → for each teacherDocument: INSERT teacher_documents (schoolId, teacherId, documentType enum, fileObjectId REFERENCES file_objects.id, uploadedAt, expiryDate?) → audit_log `action=teacher.create nested_count_qualification=… nested_count_doc=…` → return 201 `{data: teacher {+qualifications+documents}}`. Alternatives: PATCH `/teachers/:id/add-qualification` later; bulk upload via import (UC-IMP-001). Exception A: 409 TEACHER_EMPLOYEE_ID_DUPLICATE error.meta.existingTeacherId=uuid. Exception B: referenced fileObjectId does not belong to same schoolId → 403 FILE_OBJECT_OUT_OF_SCOPE (reject before insert to prevent cross-school file links). Postcondition: teachers row + 0..N qualification/doc rows all share same schoolId; employeeId unique per (school, active). Permission: teachers.create. Rules: BR-AT-020, BR-AT-021. Data/API/UI: teachers, teacher_qualifications, teacher_documents. POST teachers. Teachers list + "Add Teacher" modal. Related: UC-TEA-002 (teacher assignment), UC-FIL-004 (document upload).

### UC-ACA-003 — Class + Section hierarchies with capacity + rollover from prior year

**Actor:** school admin. **Goal:** create class (grade) and child sections; set capacity; optionally roll sections + enrollments from prior academic year. **Preconditions:** user has `academicStructures.manage`; school exists; target academic year exists and isActive. **Trigger:** POST `/api/v1/classes` body `{name, shortName, orderIndex, sections:[{name, capacity}], rolloverFromAcademicYearId?: uuid}`.

Main: Zod validates sections[].capacity ≥ 10 ≤ 100; sections[].name within same class unique (composite where: classId+name). → overlap check class name `WHERE schoolId AND name AND academicYearId = currentAY count>0` → Exception A → duplicate section name in input → Exception B → `rolloverFromAcademicYearId` present: transaction INSERT classes + sections + for each prior-year section: INSERT student_enrollments rows WHERE prior_sectionId, status='enrolled' → new_sectionId + new classId + new academicYearId; rollNo per section sequence resets per section (start at 1) per year. → audit `action=class.create nested_section_count=N`. Alternatives: "Rollover all classes" batch endpoint POST `/academic-years/:id/rollover-classes` with `{sourceAcademicYearId, dryRun?:boolean}` returns preview before apply. Exception A: 422 CLASS_NAME_DUPLICATE_IN_YEAR. Exception B: 422 SECTION_NAME_DUPLICATE_IN_CLASS. Postcondition: class sections capacity enforced (UC-STU-003 enrollment: before insert check section.enrolled_count < capacity; throw SECTION_AT_CAPACITY). Permission: academicStructures.manage. Rules: BR-AT-012, BR-AT-013. Data/API/UI: classes, sections, enrollments (sequence rollNo per section). POST classes, sections. Classes + Sections admin screens. Related: UC-ACA-007 (subject offering).

### UC-ACA-007 — Subject offering + teacher assignment scopes (class/section/subject triple)

**Actor:** school admin / academic coordinator. **Goal:** define which subjects are offered to each class/section in academic year, and assign teacher(s) with scope. **Preconditions:** subject exists; class+section exists for year; teacher exists; user has `subjectOfferings.manage` + `teacherAssignments.manage`. **Trigger:** POST `/api/v1/subject-offerings` bulk body `[{academicYearId, classId, sectionId?, subjectId, curriculumVersionId?, weeklyPeriods:number}]` followed by POST `/api/v1/teacher-assignments` `[{teacherId, subjectOfferingId, assignmentType=primary|co|substitute, effectiveFrom, effectiveTo?}]`.

Main: subjectOfferings upsert `@@unique([schoolId, academicYearId, classId, sectionId, subjectId])` → violation → skip/warn 422 SUBJECT_OFFERING_DUPLICATE → after offerings, teacher assignments: for each assignment, check triple-scope composite; same subjectOfferingId + PRIMARY teacher already exists → allow single PRIMARY only (Exception A); multiple CO teachers OK. → After assignments materialize user_scopes table rows: INSERT INTO user_scopes (userId, schoolId, scopeType='teacher_subject_offering', scopeRefId=subjectOfferingId, effectiveFrom, effectiveTo). → This drives req.user.scopes.teacherSubjectOfferingIds at login (UC-AUTH-001 userContext). → audit `action=subject_offering.create batch_size=N` + `teacher_assignment.create`.
