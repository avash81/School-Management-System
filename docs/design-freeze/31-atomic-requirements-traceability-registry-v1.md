# CR-02 — Atomic Requirements and Traceability Registry v1.0

**Status:** REMEDIATION DRAFT. This registry supersedes the broad rows in Document 02 for the items below. A test ID is a required specification case, not evidence that a test has run.  
**Rule:** a requirement is atomic only if it expresses one observable system behavior with one expected outcome. Every ID in the six trace columns is defined in this file or a linked authoritative document; blank is not permitted.

## Trace conventions

- **UC:** critical use cases in Document 03; `UC-X-nnn` IDs marked _catalogue_ must receive their full specification during HI-01, but their requirement linkage is already fixed.
- **BR:** `BR-AT-*` entries in the rule catalogue at the end of this document. These augment rather than replace Document 20.
- **Data:** exact target table names in CR-01A (Document 30a).
- **API/UI:** contract target and screen contract name; exact request/response schemas are CR-03.
- **Test:** executable-case IDs whose Given/When/Then definition must be placed in the updated Document 22 during HI-05.
- **Release:** `MVP` must be designed before the rerun audit; `R1/F` is future/deferred and has no claim of implementation.

## Atomic rule catalogue

| Rule          | Enforceable rule                                                                                                                                                       |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| BR-AT-001–004 | Authentication/session/reset behavior is as stated by REQ-AUTH-001-A through D; secrets/tokens are hashed and generic auth error messages prevent account enumeration. |
| BR-AT-005     | An unauthenticated request receives the standard 401 response and no protected data.                                                                                   |
| BR-AT-006     | Authorization is `permission AND applicable data scope`; frontend state is not an authorization decision.                                                              |
| BR-AT-007     | Every tenant query/mutation binds authenticated `school_id`; cross-tenant IDs yield the policy response without revealing existence.                                   |
| BR-AT-008–010 | Current settings are mutable; released configuration is immutable; flags never replace authorization.                                                                  |
| BR-AT-011–015 | Academic dates/references are valid and tenant-consistent; a teacher assignment is the maximum academic scope granted to a teacher.                                    |
| BR-AT-016–022 | Student/guardian/enrollment/attendance uniqueness, atomicity, historical lifecycle and correction rules are exactly as expressed in the linked requirements.           |
| BR-AT-023–024 | Exams use valid dates and an immutable applicable configuration; exam subjects use a valid offering/blueprint.                                                         |
| BR-AT-025–030 | Numeric/status validation, optimistic concurrency, submission completeness, workflow approval and correction revision are mandatory for marks.                         |
| BR-AT-031–034 | Result calculation inputs, policy processing, snapshots and publication approvals are deterministic, versioned and immutable after publication.                        |
| BR-AT-035–036 | File scan and private-download checks must succeed before use; object keys/URLs are never a substitute for authorization.                                              |
| BR-AT-037–040 | Import idempotency, provisional OCR evidence, mandatory ambiguity review and all-or-none final import transaction are mandatory.                                       |
| BR-AT-041–044 | Official document provenance, minimum-data verification, notice history and independently tracked notification delivery are mandatory.                                 |
| BR-AT-045–052 | Report/export, worker, support, performance, restore, accessibility and retention guarantees apply as stated in their linked row.                                      |

## Registry integrity checks

1. A release cannot be marked feature-complete if an MVP row lacks a use-case specification, data table, API schema, screen contract, test definition, authorization rule, or audit decision.
2. `R1/F` rows remain traceable but may not be represented as MVP behavior in endpoint/UI documentation or implementation status.
3. Change control adds a new atomic requirement ID; it never silently broadens an existing row.
4. HI-01/HI-05 must replace all `catalogue` UC references and test-ID placeholders with fully detailed linked artifacts before a rerun Phase 13 GO decision.
